# ADR 0009: Memory as a Separate HTTP Service, Not an In-Process Library

The memory layer (Graphiti + Neo4j) runs as a standalone HTTP service with its own container, config, and API — not embedded in the Workbench server process. Workbench talks to it via `HttpMemoryLayer`, a thin HTTP client implementing the existing `MemoryLayer` ABC. The memory service owns Graphiti, Neo4j connectivity, LLM-based fact ingestion, and the extraction prompt. Workbench never imports Graphiti or connects to Neo4j directly.

We chose this over embedding Graphiti in-process (Approach B) because: (1) Graphiti + Neo4j have a heavy dependency footprint (`graphiti-core`, `neo4j`, `numpy`, `openai`) that would pollute workbench's environment and slow container builds; (2) fact ingestion involves LLM calls that shouldn't compete with the pipeline's event loop; (3) the memory service can be developed, tested, and deployed independently — a different team or future maintainer can swap the implementation without touching workbench; (4) the Meta-internal override pattern (workbench-meta) works cleanly — the memory service gets its own config overlay for Plugboard LLM, same as workbench.

The trade-off is operational complexity: four containers instead of two (postgres, neo4j, memory, workbench), plus an HTTP boundary that adds latency to preference queries. For a single-user tool this is more infrastructure than strictly necessary. We accepted this because the clean separation makes each component independently testable and replaceable, and the HTTP overhead (~1-5ms for preference queries on localhost) is negligible compared to LLM call latency.

**Consequence:** The `MemoryLayer` ABC stays unchanged. `HttpMemoryLayer` is the production implementation. `NoopMemoryLayer` remains for testing and memory-disabled mode. The memory service has its own `pyproject.toml`, `Dockerfile`, and config file with `--config` + `--override` layering. If the memory service is down, the pipeline degrades gracefully (explicit filter rules only).
