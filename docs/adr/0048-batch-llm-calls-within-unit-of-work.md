# ADR 0048: Batch Non-Interactive LLM Calls Within the Unit of Work, Not via a Global Micro-Batcher

**Status:** Accepted — 2026-06-08

**Context.** To cut plugboard call volume we want to coalesce same-type non-interactive LLM calls. The two dominant fan-out points are `score_relevance` (issued serially in a `for ext_item in extracted` loop inside `process_raw_item`, one call per extracted item) and `score_urgency`. **`score_urgency` is NOT issued in the scheduler loop directly** — it is called inside `PipelineEngine.enqueue` (`engine.py`, the `if self.queue_scorer and urgency_signals:` branch), which the scheduler invokes once per raw item from BOTH its enqueue paths: the non-monitoring branch of `_poll_one_source` and `_route_poll_results` (monitoring-capable sources). So the per-poll fan-out is one `enqueue`→`score_urgency` per new raw item. A classic time-window/DataLoader micro-batcher coalesces *concurrent* requests arriving within a wait window — but these calls are issued **serially** (each await completes before the next is issued), so a window batcher literally cannot coalesce them without first refactoring the call sites to fire concurrently. The fan-out set is already known synchronously at each call site.

**Decision.** Batch **within the natural unit of work** rather than with a global real-time batcher. Add `score_relevance_many(items, preference_facts, rules)` and `score_urgency_many(items)` to the provider interface; refactor `process_raw_item` to score all extracted items of a raw item in one call. For urgency, **hoist the score out of `PipelineEngine.enqueue`**: add an `enqueue_prescored(...)` path (or an explicit `urgency_score` param to `enqueue`) so the scheduler can pre-score all un-processed raw items of one poll in one `score_urgency_many` call, then enqueue each with its precomputed score (no second per-item scorer call). **Both scheduler enqueue paths** (`_poll_one_source` non-monitoring branch and `_route_poll_results`) must use the pre-scored path; in `_route_poll_results` the new-item subset is pre-scored before the per-item change-detection loop. Multi-item prompts use a JSON array with explicit per-item `index`; results are matched back by index. On whole-batch failure, the existing `_call_with_retry` 3× exponential backoff runs; on exhaustion or any missing/malformed sub-result, the code falls back to the existing **per-item** method (the correctness floor). `extract`, `generate_triage_card`, and the interactive `interpret_triage_response` are **not** batched. A `batching:` config section (`enabled`, `score_relevance`, `score_urgency`, `max_batch_size=20`) gates it, read at each call site (no background state → hot-reload-safe). When `batching.score_urgency=false`, the scheduler falls back to per-item enqueue (scorer called inside `enqueue` as today).

**Consequences / Alternatives.** This sets the provider-interface shape (`_many` methods), the engine/scheduler control flow, AND the `enqueue`/`enqueue_prescored` contract change, so it earns an ADR. We rejected (a) a DataLoader-style time-window micro-batcher with futures — serial awaits defeat it, and it would add a background flush task, pending-future bookkeeping, added latency, and shutdown teardown for no benefit on a single-user low-volume tool; (b) coalescing only across the 2 concurrent worker entries — batch size ≈ 2, negligible; (c) the Anthropic Message Batches async API — 50% cheaper but adds a pending-state to the durable queue and minutes-to-hours latency. **Note:** `LLMQueueScorer` currently sets `max_tokens=100`, which cannot hold N urgency results — `score_urgency_many` must raise the output cap proportional to batch size (`min(4096, 40 * len(items) + 100)`; safe against truncation at `max_batch_size=20`).
