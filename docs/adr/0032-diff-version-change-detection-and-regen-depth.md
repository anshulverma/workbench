# ADR 0032: Detect Diff Code Changes via a `diff_version` Signal; Key Regeneration Depth on `change_type`

The `PhabricatorChangeDetector` is synchronous and metadata-only (it compares two poll dicts, no network, no LLM), but rich diff cards must regenerate their curated hunks when the author uploads new code. We add a **`diff_version`** field to what the Phabricator `poll()` captures (the active code-diff version identifier on the revision — an opaque value compared by equality), and make a `diff_version` change a material field producing `change_type="code_updated"`. The `updated` timestamp is **not** used (it also advances on comments/status); `revision_id` (`D{number}`) is the stable item key and never changes across revisions.

We then key **regeneration depth on `change_type`** (a two-tier cost gate): `code_updated` → full path (`_fire_retriage` re-runs the `DiffEnricher` to re-fetch the diff and the `DiffCardContentGenerator` to regenerate curated hunks); `status_changed` / `ci_changed` / `comment_added` → light path (reuse the stored hunks at `card_content.sections.hunks`, regenerate only the change-aware summary/risk/why-care copy and options). On a debounced window mixing code and non-code changes, the merged `change_type` resolves to the heaviest (`code_updated`).

We chose this over always re-fetching the diff on every material change because status/CI/comment changes are the common case and carry no code change — re-fetching the full diff and re-running Opus for them is wasted cost with no quality gain (the stored hunks are still accurate). Critical changes (CI failure on an authored diff) take the light path: reuse hunks, add the CI-failure watch-out, bypass the daily cap.

**Consequence:** `poll()` must persist `diff_version` into `Item.raw_data` so the detector can compare old vs new. The exact `meta phabricator.diff list/get` field name is unconfirmed and is part of the implementation verification task; the fallback is a coarse proxy (line-count / files-changed). The light path requires the prior enrichment's `curated_hunks` to be readable from the card (`card_content.sections.hunks`).
