# ADR 0047: Add a Real `triage_cards.created_at` Column to Power the Triage Time-Window Filter

**Status:** Accepted — 2026-06-08

**Context.** The redesigned Triage page (ADR 0043) adds a client-side Time-Window filter (LAST 1H / 24H / 7D / ALL) over the fetched pending cards. That filter needs each card's age, but `triage_cards` records only lifecycle timestamps — `sent_at`, `expires_at`, `responded_at`, `deferred_until` — and **no row-birth timestamp**. `sent_at` is null for not-yet-sent (`queued`) cards, so it cannot stand in for "age". The user asked to build the time filter and to "do it right" to avoid a future migration.

**Decision.** Add a real **`created_at TIMESTAMPTZ NOT NULL DEFAULT now()`** column to `triage_cards` via a new Alembic migration (`007`, `down_revision = "006"` — the existing head is `006_change_monitoring_indexes`), indexed (`idx_triage_created_at`). Add a matching `created_at` field to the `TriageCard` model (default `datetime.now(timezone.utc)`), persist/read it in `PgTriageStore.save_card` / `_row_to_card`, and serialize it on the `GET /api/triage/pending` payload (the endpoint returns Pydantic `TriageCard` models, so it serializes via `model_dump(mode="json")`). There is **no separate `queued_at` column**: the queue lifecycle is `queued → sent → responded/expired` (CONTEXT.md "Triage Queue"), so a card's "queued" age is exactly its `created_at`.

**Consequences / Alternatives.** This is a schema change (a forward DB migration is hard to reverse cleanly once rows exist), so it gets an ADR. We rejected (a) reusing `sent_at` — null for queued cards, wrong semantics; (b) deriving age from the `id` UUID — UUIDv4 carries no time; (c) adding both `created_at` and `queued_at` — redundant given the lifecycle. The `DEFAULT now()` backfills existing rows at migration time with the migration timestamp (acceptable: those are pre-feature cards). The new column also gives every future "card age / dwell time" metric an honest source without another migration.
