# ADR 0017: Management Dashboard Auth and Secret-Exposure Model

The `/ui` SPA authenticates by fetching the bearer token from the **Token-Vending Endpoint** `GET /api/auth/token`, which is auth-exempt (the `BearerTokenMiddleware` already whitelists `/ui*` and `/api/auth/token`). This is acceptable **only** because the server is reachable solely over an SSH tunnel by a single user; we therefore recommend binding the server to loopback (`127.0.0.1`/`::1`) and treating the tunnel as the security boundary. Separately, every read endpoint that serializes config-derived data must pass it through a shared `redact_secrets()` (promoted from `api/debug.py` to `workbench/redaction.py`); new endpoints use **allowlist-on-output** (return only named safe fields), with the key-name denylist as a backstop. The bearer token is the only secret that ever reaches the browser — never `service_account_key_path`, tokens, DSNs, or credentials.

We chose the auth-exempt token-vend (keeping the mechanism, fixing the stale docstrings that wrongly describe a cookie/query-param scheme) over inventing session/cookie auth, because under loopback isolation an attacker who can call the endpoint already controls the host. We chose allowlist-on-output over relying on the regex denylist alone because a future secret field that does not match the regex would silently leak; a security-critical surface must fail closed.

The trade-off is that the token has low intrinsic value behind the tunnel and the model breaks if the port is ever exposed off-host — hence the loopback-bind recommendation is load-bearing, not optional. Allowlisting also costs a little boilerplate per endpoint.

**Consequence:** No CORS is configured (the SPA is same-origin at `/ui`). The frontend bans `dangerouslySetInnerHTML`. The `adapter_type` allowlist (never a raw dotted class path) guards `POST /api/sources` against import-gadget execution. Config-mutating endpoints emit structured audit logs with the request **Correlation ID**.
