# ADR 0049: Two-Layer LLM Instrumentation (Method-View Decorator + Transport-View Call-Site Shim) with Sink Injection

**Status:** Accepted — 2026-06-08

**Context.** We need per-`client`+`model` plugboard metrics — calls, tokens, latency, errors — to measure and reduce call volume. The existing `InstrumentedLLMProvider` decorator wraps the provider *interface methods* and sees only the returned domain objects, so it cannot observe token usage, the model string, or the `client` identity. Those are only in scope at the actual `messages.create` call site (`response.usage`, `self.model`, the owning class). The provider classes are pluggable and resolved via YAML dynamic import, so they must not depend on `workbench.metrics`.

**Decision.** Run **two layers**. (1) Keep the existing `InstrumentedLLMProvider` method-view decorator (latency-by-method, `llm_calls{method}`) unchanged. (2) Add a transport-view **call-site shim** — a free helper `src/workbench/providers/_plugboard.py` wrapping `messages.create`, called by `AnthropicLLM._call_with_retry`, `AnthropicLLM.interpret_triage_response`, and `LLMQueueScorer.score_urgency` (Meta subclasses inherit). It emits a `PlugboardCallRecord` (client, model, input/output/cache tokens, latency, error_type, item_count) to a **constructor-injected sink** (`on_plugboard_call`, default no-op); the workbench-side sink — wired in lifespan, closing over `app.state.metrics` and the usage aggregator — owns all Prometheus knowledge. New metrics: `plugboard_calls_total`, `plugboard_call_seconds`, `plugboard_tokens_total{direction}`, `plugboard_errors_total{error_type}`, `plugboard_items_total`, all labeled `{client, model}`; existing `llm_*{method}` metrics are left intact (no breaking relabel).

**Consequences / Alternatives.** The two layers intentionally disagree — the shim counts each HTTP attempt (retries inflate it) and folds batched items, while the decorator counts logical operations — which is correct, not a bug, and documented in CONTEXT.md. Sink injection (vs. importing `WorkbenchMetrics` into providers) is what preserves provider pluggability; reversing it later would touch every provider constructor. We rejected (a) relabeling the existing `llm_*` metrics with `model`/`client` — a breaking change for any recording rule/dashboard, the opposite of "extend"; (b) wrapping the `AsyncAnthropic` client object — it wouldn't know the `client` identity and couples to the SDK surface (streaming, beta namespaces). Token capture is unconditional when `metrics.enabled`; `DebugConfig.llm_token_usage` gates only verbose per-call logging.
