# ADR 0014: Per-Source Cron Jobs and Per-Source Watermarks

Each enabled source gets its own APScheduler `CronTrigger` job (a **Source Job**, id `poll_source:{source_id}`, built via `CronTrigger.from_crontab(schedule, tz=logging.timezone)`, `max_instances=1`, `coalesce=True`), replacing the single global interval job that polled all sources together. `SchedulerConfig.poll_interval_minutes` is demoted to driving the `alert_check` job only. Polling state moves from `source_last_polled:{adapter_type}` to `source_last_polled:{source_id}` (the **Watermark**) in `stores.config`, and both scheduled and manual polls run through one `_poll_one_source(source_id, trigger)` method guarded by a per-source `asyncio.Lock`.

We chose real per-source cron (the user's explicit choice) over keeping the global interval with a per-source "is it due?" check because the latter re-implements cron poorly and cannot reschedule a single source live. We chose `source_id` watermarks because the old `adapter_type` key collides whenever two sources share an adapter type (e.g. two GitHub sources), causing them to share one `since` cursor.

The trade-off is an upgrade migration: existing watermark keys are `{adapter_type}` and source entries had no stable id. We assign each YAML source a stable `id` (a config-format change requiring a config `version` bump) and perform a **one-time non-destructive migration** that renames `source_last_polled:{adapter_type}` to the corresponding `source_id`, so upgrading does not trigger a full re-poll ("poll storm"). For the genuine two-same-type case there is no clean automatic split — one inherits the watermark, the other starts fresh.

**Consequence:** Disabling a source removes its Source Job (no more no-op polling of disabled sources). Runtime add/edit/delete call `add_job`/`reschedule_job`/`remove_job`. Cron strings are validated at the API boundary via `from_crontab` (no `croniter` dependency added — APScheduler 3.10 already validates). Startup staggers first runs to avoid a simultaneous poll burst.
