# ADR 0031: Symmetric `CardMessage` Delivery for Both Send and Update

Combining the two features reconciles their messenger changes: the change-monitoring `update_message(message_id, text: str) -> bool` becomes **`update_message(message_id: str, card: CardMessage) -> bool`**, symmetric with the diff-cards `send_card(card: CardMessage) -> str` (ADR 0026). The presenter builds one `CardMessage`; each messenger renders it to its wire format for both send and update. Re-triage (`_fire_retriage`) drives the same `CompositeCardPresenter → CardMessage` path instead of `format_card_for_chat` plain text.

We chose symmetry over keeping a text-based `update_message` because an asymmetric interface would lose the rich cardsV2 card on every update (a re-triaged diff would degrade to plain text). The base `Messenger.update_message` default returns `False`; `ConsoleMessenger` prints `render_to_text(card)`; `GoogleChatMessenger` patches the parent cardsV2 (a new `update_card_message` helper in `workbench_meta/lib/google_api.py` patches `updateMask=cardsV2,text`, since the existing helper only updates text). The existing `TriageCard.bot_message_id` (parent message resource name) is reused for send, update, and `poll_responses` — no new id field; an optional `thread_name` field is added for completeness.

**Consequence:** On `update_message` returning `False`, the caller falls back to `send_card(card)` and **must re-persist the returned `bot_message_id`** (and `thread_name`), or `poll_responses` will anchor on a dead message. For v1, an in-place update patches only the parent card and marks "[Updated]" in the `CardMessage.header`; previously-posted threaded hunk replies are left stale (the parent links out to the diff). Deleting/reposting hunks on update is deferred.
